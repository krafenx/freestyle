# Готовый промпт для агента/разработчика

Ниже — самодостаточное ТЗ. Скопируй целиком, подставь значения в блоке `КОНТЕКСТ` (всё, что в
`{{...}}`), и отдавай агенту. Если поле не заполнено — агент обязан взять дефолт из раздела

## ПРОМПТ (копировать отсюда)

**Роль.** Ты senior-разработчик, который делает небольшие продакшн-боты на TypeScript. Ты пишешь
код, который сможет поддерживать человек, открывающий его через полгода: без магии, с тестами на
критичную логику и с понятными сообщениями об ошибках в чат.

**Задача.** Сделать Telegram-бота для учёта Twitch-VIP, выдаваемых на ограниченный срок. Бот
помнит, кому и когда выдан VIP, считает дату окончания, присылает напоминания модераторам и (в
полном режиме) сам выдаёт и снимает VIP через Twitch Helix API.

### КОНТЕКСТ

- Канал Twitch: `{{CHANNEL_LOGIN}}` (`{{BROADCASTER_ID}}`).
- Заказчик — **модератор** канала, не владелец. Значит по умолчанию у нас **нет** токена стримера.
- Срок VIP по умолчанию: `{{30 дней}}`. Продление: `{{стопкой: новый срок = max(сейчас, текущая дата конца) + период}}`.
- Выдача бывает: `{{каналпоинты (награда «VIP на месяц») / вручную за активность / донат}}`.
- Пользователи бота: `{{2–3 модератора, приватная группа в Telegram}}`.
- Часовой пояс отображения: `{{Europe/Moscow}}`, время напоминаний: `{{10:00}}`.
- Хостинг: `{{Cloudflare Workers + D1}}` (см. «Дефолты», если не указано).
- Режим работы: `{{B → C: сейчас только напоминания, но автоматизация выдачи/снятия должна
  включаться флагом без переписывания кода}}`.

### ЖЁСТКИЕ ТРЕБОВАНИЯ

1. **Никаких auto-действий по умолчанию.** Снятие VIP через API выполняется только если
   `AUTO_REMOVE=true`. Иначе бот присылает напоминание с кнопкой «✅ Снял»/«➕ Продлить».
2. **Один источник правды — база.** Всё состояние в БД, в памяти процесса ничего не хранится.
   Крон и вебхук могут выполняться параллельно в разных инстансах — код обязан быть идемпотентным.
3. **Время только в UTC в БД.** Рендер в целевом поясе через tz-базу (`Intl`/Luxon, не «+3 часа»).
4. **Идемпотентность напоминаний**: перед отправкой пишем в `notifications_log` с
   `UNIQUE(grant_id, kind)`; если запись уже есть — не отправляем. Ошибка отправки не должна
   «съедать» напоминание навсегда — допускается повторная попытка со статусом `failed`.
5. **Дедуп внешних событий**: `event_id` (у Twitch — `Twitch-Eventsub-Message-Id`, у редима —
   `redemption.id`), `UNIQUE` в БД, повтор молча игнорируется.
6. **Никаких секретов в коде и в логах.** Токены — в env/secrets; Twitch `refresh_token` стримера
   шифруется (AES-GCM, ключ в env); в логах токенов нет даже частично.
7. **Whitelist доступа**: любой апдейт от Telegram, чей `from.id` не в списке разрешённых, получает
   «нет доступа» и пишется в лог. Без исключений, включая callback-кнопки.
8. **Понятные ошибки в чат.** Любой не-2xx от Twitch/Telegram → сообщение в чат модераторов с
   кодом, телом и что делать. Молчаливых `catch {}` быть не должно.

### ФУНКЦИОНАЛ

**Модуль 1. Учёт (ядро, не зависит от Twitch).**

- `/vip add @nick [30d] [--to YYYY-MM-DD] [--note ...]` — создать выдачу. Логин резолвится в
  `twitch_user_id` через Helix `GET /users?login=`; если Twitch недоступен — сохранить как
  `pending_resolve` и дорезолвить в кроне, не терять запись.
- `/vip list [--expiring] [--expired] [--all] [--sort date|name]` — активные по умолчанию.
- `/vip info @nick` — вся история по человеку (выдачи, продления, снятия, кто и когда).
- `/vip extend @nick [+30d|--to DATE]` — продление по политике из контекста, с записью в аудит.
- `/vip remove @nick [--reason]` — закрыть запись; `--twitch` — реально снять VIP (только в режиме A).
- `/vip keep @nick` — «оставляем», запись переходит в `keep`, повторное напоминание через 7 дней.
- `/vip cancel @nick` — отменить ошибочную запись (soft-delete, остаётся в истории).
- `/vip sync` — сверка с `GET /helix/channels/vips` (пагинация), три исхода: «в базе есть, в канале
  нет», «в канале есть, в базе нет», «совпало». По первым двум — инлайн-кнопки
  «закрыть запись» / «завести запись».
- `/vip export` — CSV (файлом в чат).
- `/vip stats` — выдано за период, активных, средний срок, топ по продлениям.
- `/vip help` — краткая справка. Все команды — с подсказками через `setMyCommands`.

**Модуль 2. Напоминания (крон).**

Окна: `T−3 дня`, `T−1 день`, `T−0 (в 10:00 локального)`, `просрочено (T+0 23:59)`, эскалация
`каждые 7 дней, максимум 4`, недельный дайджест (пн 10:00). Правила:
- не более одного сообщения на запись в сутки;
- **catch-up**: если последний успешный прогон был > 3 часов назад, отправить один сводный дайджест,
  а не пачку;
- под каждым сообщением — инлайн-кнопки `✅ Снял`, `➕ Продлить 30д`, `📅 +7д`, `🙈 Оставить`,
  `⏰ Завтра`; `callback_data` — непрозрачный короткий токен, живущий в БД (не «сырой» id);
- отдельное **запиненное сообщение-дашборд**, которое бот редактирует после каждого изменения:
  ближайшие 5 истечений, число активных, число свободных слотов (если известно).

**Модуль 3. Twitch: приём событий (EventSub, webhook).**

- Эндпоинт отвечает на `challenge` **плоским текстом** (не JSON!) в течение 10 секунд — иначе
  подписка не создастся.
- Проверка HMAC: `HMAC-SHA256(secret, message_id + timestamp + raw_body)` сравнение с
  `Twitch-Eventsub-Message-Signature` (`sha256=...`), сравнение постоянного времени, тело — **до**
  парсинга JSON.
- Подписка `channel.channel_points_custom_reward_redemption.add` (условие: `broadcaster_user_id`,
  опционально `reward_id`) — создаётся скриптом `npm run twitch:subscribe` (идемпотентно: сначала
  `GET /eventsub/subscriptions`, потом создать отсутствующие), а не «руками в доке».
- На редим: создать `vip_grant` (`source='channel_points'`, `expires_at=now+период`,
  `redeemed_id=<id>`), отправить в чат «🎁 @nick забрал VIP до DD.MM», при `AUTO_GRANT` — выдать VIP
  и пометить редим `FULFILLED` (`PATCH /channel_points/custom_rewards/redemptions`), иначе оставить
  `UNFULFILLED`.
- Если в актуальном списке EventSub есть типы про VIP — подписаться и на них; если нет, не выдумывать,
  а полагаться на сверку из модуля 1 (в README об этом написать явно).

**Модуль 4. Twitch: действия (только режим A).**

- Интерфейс `VipProvider { addVip(userId), removeVip(userId), listVips(): AsyncIterable<Vip> }` с
  двумя реализациями: `ManualVipProvider` (ничего не делает, только логирует) и `HelixVipProvider`.
  Выбор — флагом `VIP_PROVIDER=manual|helix`.
- Helix-реализация: OAuth Authorization Code flow, `state` в подписанной cookie/KV, скоупы
  `channel:manage:vips`, `channel:read:redemptions`, `channel:manage:redemptions`,
  `channel:read:vips`. **Важно: `broadcaster_id` в запросах VIP обязан совпадать с user_id
  владельца токена** — то есть токеном модератора эти эндпоинты не работают; в коде это
  задокументировать комментарием, чтобы через месяц никто не искал баг «403/401».
- Refresh: хранить `access_token`, `refresh_token`, `expires_at`; обновлять за 5 минут до истечения;
  **refresh-токен ротируется** — сохранять новый атомарно, иначе бот потеряет доступ.
- Обработка кодов: `409` нет свободных слотов → `status='waitlist'` + алерт «освободите слот»;
  `422 already a VIP` → трактовать как продление; `422 user is a moderator` → алерт «сначала снимите
  мод»; `400 blocked` → алерт; `425` → алерт «канал не выполнил Build a Community».
- Проверить `GET /channels/vips` также при выдаче: если уже VIP — не выдавать повторно, а продлить.

### МОДЕЛЬ ДАННЫХ

Реализуй ровно эти таблицы (SQLite/D1-совместимо), с индексами:

`vip_grants`, `notifications_log`, `audit_log`, `settings`, `oauth_tokens`, `callback_tokens`.
Поля и индексы — в приложенном `schema.sql` (используй его как основу, не меняй семантику
`status`/`expires_at`). Обязательное ограничение: у одного `twitch_user_id` не может быть больше
одной записи в статусе `active`.

Статусы: `pending`, `active`, `expiring`, `expired`, `removed`, `keep`, `waitlist`, `cancelled`.
Переходы — только через функции репозитория (`grantRepo.add/extend/remove/keep/expire`), прямых
`UPDATE` из обработчиков нет.

### ТЕХНИЧЕСКИЕ ДЕТАЛИ, КОТОРЫЕ ЛЕГКО ПРОВАЛИТЬ

- Telegram: `setWebhook` с `secret_token`, проверка `X-Telegram-Bot-Api-Secret-Token`,
  `allowed_updates=["message","callback_query"]`, ответ на callback — `answerCallbackQuery` (иначе
  у пользователя крутится «часики»); редактирование сообщения вместо отправки нового при нажатии
  кнопки.
- Twitch: `Client-Id` + `Authorization: Bearer` в каждом запросе; 401 → один retry после refresh,
  потом алерт. Rate limit: учитывать `Ratelimit-Remaining`, при 429 — backoff с `Ratelimit-Reset`.
  Массовые операции — не чаще 10 VIP за 10 секунд.
- Крон: `scheduled` handler, каждый час (`0 * * * *`) + отдельный еженедельный для дайджеста;
  запись `last_run_at` в `settings`, алерт если пропуск > 3 часов.
- Логи структурированные (JSON), уровни, никаких токенов; ошибки — в чат модераторов.

### ТЕСТЫ (обязательны, до фичи)

1. Юнит: `addPeriod(now, 30d, tz)` — включая переход на летнее/зимнее время и конец месяца.
2. Юнит: политика продления «стопкой» при истёкшей и при активной випке.
3. Юнит: выбор напоминаний на моке времени — T−3/T−1/T−0/просрочка/эскалация/дайджест; проверка
   «не больше одного в сутки» и «повторный прогон крона не дублирует отправку».
4. Юнит: HMAC-валидация вебхука Twitch (валид/невалид/старый timestamp).
5. Юнит: маппинг кодов Helix (409/422/400 → статусы и тексты).
6. Интеграционный: два прогона крона подряд → ровно одно сообщение (мок Telegram-клиента).
7. Интеграционный: редим → запись создана; повторная доставка того же события → дубля нет.

### НЕ ДЕЛАЙ

- Не пиши свой планировщик на `setTimeout`/`setInterval` — на serverless это не работает.
- Не используй in-memory cache как источник правды.
- Не удаляй записи физически (только `cancelled`/`removed`).
- Не добавляй «умные» авто-продления без явного решения заказчика.
- Не тяни тяжёлые ORM/фреймворки ради 6 таблиц.
- Не изобретай EventSub-типы, которых нет в документации: если список VIP не приходит событиями —
  используй периодическую сверку.

## Мини-версия промпта (если нужно быстро, MVP за вечер)

> Сделай Telegram-бота (TypeScript, Cloudflare Workers + D1, webhook) для учёта Twitch VIP на 30
> дней. Команды: `/vip add @nick [30d]`, `/vip list`, `/vip info @nick`, `/vip extend @nick`,
> `/vip remove @nick`, `/vip export`. Таблицы: `vip_grants(id, twitch_user_id, login, source,
> granted_at, expires_at, status, granted_by, notes)`, `notifications_log(grant_id, kind,

> «просрочено», под сообщением кнопки «✅ Снял / ➕ Продлить 30д / 🙈 Оставить». Время в UTC, рендер
> в Europe/Moscow. Доступ — whitelist `tg_user_id`. Twitch API не используем: логин храним как
> строку, VIP выдаёт и снимает человек руками. Идемпотентность обязательна, тесты на выбор
> напоминаний — обязательны. Отдай: код файлами, миграции, `.env.example`, README с деплоем за 15
> минут.
